# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Spa Như Nguyệt: a foundation monorepo for a spa management system. It has an ASP.NET Core (.NET 9) backend, a React + Vite web app and a React Native + Expo (SDK 57, Expo Go) mobile app. So far it holds only the structure, the UI shell and the system-check API (`/api/v1/system/ping`, `/health/live`, `/health/ready`). Business screens show "Tính năng đang được phát triển" as a placeholder. User-facing text and the docs are in Vietnamese.

## Domain in one paragraph

This is a graduation thesis project. Four actors: guest, customer, staff (technician) and owner. Customers browse spa services and multi-session packages, add them to a cart, and pay online. A paid order creates entitlements: a `ServiceEntitlement` for a single service, or a `CustomerPackage` with a `TreatmentPlan` of ordered `TreatmentSession`s. There are two ways to book an `Appointment`. "Book now" holds the slot until payment succeeds. Booking from an entitlement or session needs no payment. The core algorithm finds free slots from staff `WorkSchedule`s and staff skills, and prevents double-booking with an in-transaction check plus a PostgreSQL `EXCLUDE` constraint. Staff write a `SkinProfile` per visit and mark sessions complete, which updates package progress. Other features: promotions, reviews, an AI assistant that gives service advice but never medical diagnoses, notifications, and revenue reports by month, quarter and year. There are 34 use cases, `UC-SPA-01` to `UC-SPA-34`.

**Staff and work schedules (UC-SPA-22/23) are done in the backend:** `/api/v1/staff` (owner: create, edit, skills, resign; everyone: a public list of working staff without contact details) and `/api/v1/work-schedules` (owner; `POST /work-schedules/batch` adds one shift per selected weekday over a range and returns `created` + `skipped` with a reason instead of failing the whole request), behind the `staff.manage` and `schedule.manage` policies. Creating staff mails a generated temporary password (never in the response or logs); a resignation can be dated in the future and `AuthService` refuses staff sign-in and refresh from that date (BR-STF-05, no background job). Active shifts of one staff member cannot overlap: an in-service check plus the `ex_work_schedules_no_overlap` `EXCLUDE` constraint (migration `AddWorkScheduleOverlapConstraint`, translated to `409 shift_conflict`). "Occupying appointment" has one definition, `AppointmentOccupancy`, for booking to reuse. Times travel as `HH:mm` (`HourMinuteTimeOnlyJsonConverter`). **Cart, orders, VNPay payment and promotions (UC-SPA-10/11/14) are done in the backend:** `/api/v1/promotions` (owner, `promotion.manage`; codes stored upper-case, code/type/value frozen once a use counts), `/api/v1/me/cart` (`cart.self`; no duplicate product, at most `Cart:MaxItems`), `/api/v1/me/orders/preview`, `/me/orders` (cart or `buy_now`, prices re-read from the catalog, optional `Idempotency-Key`), `/me/orders/{id}`, `/me/orders/{id}/payments` (`order.self`). Payment goes through the `IPaymentGateway` port; `VnpayPaymentGateway` signs with HMAC-SHA512 (`VNPAY_TMN_CODE`, `VNPAY_HASH_SECRET`, `PAYMENT_PUBLIC_API_BASE_URL`, `PAYMENT_WEB_RETURN_URL`, `PAYMENT_MOBILE_RETURN_URL` in .env; missing keys only make the payment endpoint return 503; tests use `FakePaymentGateway`). Results arrive at `GET /api/v1/payments/vnpay/ipn` and `/return/{web|mobile}`, both handled by one idempotent `PaymentService.ProcessCallbackAsync` under an order row lock; the return URL records results only when `Vnpay:ProcessReturnUrl` is true (Development). A paid order creates entitlements once (`EntitlementIssuer`: `ServiceEntitlement`, or `CustomerPackage` + `TreatmentPlan` + `TreatmentSession`s) and removes the bought products from the cart. The first hosted job, `OrderExpiryJob` (`OrderExpiry:*`), expires unpaid orders after `Order:PaymentTimeoutMinutes` (15) + grace; a late valid success still revives an expired order (Q-20). Migration `AddOrderingConstraints`. Spec: `docs/specs/orders.md`.

**Availability and owner appointment management (UC-SPA-17) are done in the backend:** `GET /api/v1/availability` (anonymous; a customer Bearer hides slots clashing with the customer's own appointments, an owner Bearer may pass `appointmentId` to compute slots for rescheduling) and `/api/v1/appointments` (owner, `appointment.manage`: list with date range ≤ 42 days, staff, status and accent-insensitive customer search; `confirm`, `reschedule`, `assign-staff`, `cancel` with a reason that gives the entitlement or session back, `no-show` after the start time; `GET /appointments/{id}` also for the assigned staff member). The service of an appointment is derived, not stored (session → entitlement's order line → own order line, `AppointmentServiceSource`, Q-25), and `ck_appointments_source` requires at least one source (migration `AddAppointmentBookingConstraints`, which also adds the `(customer_id, date)` index). Writes lock the appointment row, then the staff row (and the customer row when the time changes), so concurrent moves into one slot give `409 slot_unavailable` / `customer_busy` instead of a deadlock or a double booking; held slots past their expiry are turned into `hold_expired` lazily before a slot is written. Limits in `appsettings.json`: `Booking:SlotStepMinutes` (30, Q-11), `Booking:MaxDaysAhead` (60), `Booking:MaxQueryRangeDays` (42), `Booking:NoShowConsumesEntitlement` (false, Q-07). Spec: `docs/specs/bookings.md` (customer booking flows are wave 2).

**Customer booking and purchases (UC-SPA-15/18) are done in the backend:** `/api/v1/me/appointments` (`appointment.self`): `POST book-now` holds a slot (`held`, `hold_expires_at_utc` = order due + `OrderExpiry:GraceMinutes`, so 15 + 5 min, Q-03) and creates its one-line order through the shared `OrderPlacement` (same pricing, promotion and `Idempotency-Key` as `POST /me/orders`; a 0 đ order confirms at once); a successful payment makes `EntitlementIssuer` create the entitlement as `booked` and confirm the hold, a result after the hold expired leaves the entitlement `available` (Q-27), a failure keeps the hold unless `Booking:ReleaseHoldOnPaymentFailure` (Q-28), and `OrderExpiryService` expires holds with their orders. `POST /me/appointments` books with a bought service or package session (`confirmed`, Q-02; session order, gap and package expiry in `EntitlementEligibility`, BR-BKG-05), `GET /me/appointments/{id}` shows the customer's own appointment. Both flows go through `BookingSlotReserver` (lock candidate staff in id order, then the customer; "any staff" picks the least busy, `Booking:AutoAssignStrategy` = `least_busy`, Q-26). `GET /availability` also takes `serviceEntitlementId` / `treatmentSessionId` for a customer. `/api/v1/me/purchases` (`purchase.self`, new `Purchases` folder) lists bought services and packages with an effective status computed on read (no expiry job yet, Q-32), `canBook` and the package's `nextSession` with its earliest date; `Purchases:MaxListItems` (200) caps each list. No migration. Specs: `docs/specs/bookings.md` (wave 2), `docs/specs/purchases-treatments.md`.

**Staff appointments and care (UC-SPA-25/27/28) are done in the backend:** `GET /api/v1/me/assigned-appointments` (`schedule.self`; date range ≤ `Booking:MaxQueryRangeDays`, never `held`/`hold_expired`, Q-33) with the detail at the existing `GET /appointments/{id}` (now with allergy ids, `treatmentSession.totalSessions/packageName`, `skinProfileId`). New `Care` folder, `care.write` policy (staff): `GET|POST /appointments/{id}/skin-profile`, `PUT /skin-profiles/{id}` (only the assigned staff member writes; a `confirmed` visit from its date or a `completed` one up to `Care:SkinProfileEditWindowDays` (7) days later, Q-34; one profile per appointment, `ux_skin_profiles_appointment_id` → `409 skin_profile_exists`), `/customers/{id}/allergies` GET/POST/PUT/DELETE (staff with a pending/confirmed/completed appointment with the customer, owner reads only, duplicate allergen ignoring case and accents → `409 allergy_exists`, Q-36), and `POST /appointments/{id}/complete` (assigned staff, `confirmed`, from the start time; entitlement → `used`, or session `completed` + package `used_sessions`, plan start/end on the visit date; `Care:RequireSkinProfileToComplete` = false, Q-35). No migration. Specs: `docs/specs/care.md`, `docs/specs/staff.md` (UC-SPA-25).

**Treatments and service history (UC-SPA-19/20/21) are done in the backend:** `/api/v1/me/treatments[/{id}[/sessions/{sessionId}]]` (`purchase.self`): progress, every session in order with `canBook`/`reason`/`earliestDate` from the same `EntitlementEligibility` as booking, the current appointment and the session result; the plan's internal note and skin profiles stay hidden (`Treatments:ShowSkinProfilesToCustomer` = false, Q-39). `/api/v1/me/service-history[/{appointmentId}]` lists the customer's `completed` and `no_show` visits (Q-40), paged, filtered by date, derived service and status. `/api/v1/treatments` (`treatment.manage`, owner + staff; new `Treatments` folder): accent-insensitive search, detail with sessions, skin profiles and care history, `PUT` goal/expected end date/note and session notes (owner or primary staff; staff never edit a completed session), and owner-only `assign-staff`, `pause`/`cancel` with a reason (new column `treatment_plans.status_reason`, migration `AddTreatmentPlanStatusReason`), `resume`, `complete` (close a plan left with skipped sessions). Cancelling needs no booked session and cancels the package (no refund, Q-38). Staff see plans they lead and, with `Treatments:AssignedStaffCanView` (true, Q-37), plans with one of their session appointments (read only). Spec: `docs/specs/purchases-treatments.md` (wave 2).

**My appointments (UC-SPA-16) are done in the backend:** `GET /api/v1/me/appointments` (`appointment.self`; `scope` = `upcoming` (held/pending/confirmed, ascending) | `past` (completed/no-show) | `cancelled` (cancelled/hold-expired), plus `status`, `fromDate`/`toDate`, paged), `POST /me/appointments/{id}/reschedule` (`{ date, startTime, staffMemberId? }`, no staff = any staff, keeps the length and status) and `POST /me/appointments/{id}/cancel` (`{ reason }`, gives back the entitlement or session, no refund). Both need a `pending_confirmation`/`confirmed` appointment at least `Booking:CustomerChangeCutoffHours` (24, Q-04) before its current start, else `400 change_window_passed`; held appointments cannot be changed by the customer (Q-41). One pure rule, `AppointmentChangePolicy`, decides the commands and the `canReschedule`/`canCancel`/`changeDeadlineAtUtc` fields (`MyAppointmentReader`). Moving a package session keeps the package order: not before the earliest date after the previous visit, not after the next session's visit minus its gap (`400 session_too_late`, Q-42; `SessionBookingFacts.Next`). `GET /availability?appointmentId=` with a customer Bearer (instead of a source) returns slots for moving that customer's own appointment (BR-BKG-18). Reschedules lock the appointment, then go through `BookingSlotReserver` with `excludeAppointmentId`. No migration; reschedules are unlimited (BKG-LATER-08). Spec: `docs/specs/bookings.md` (wave 3).

**Order list and cancellation (UC-SPA-12/13) are done in the backend:** `GET /api/v1/me/orders` (`order.self`; `status`, `fromDate`/`toDate` on the Vietnam date of creation, newest first, `isPayable`/`canCancel` from one `OrderActionPolicy`) and `POST /me/orders/{id}/cancel`; owner `/api/v1/orders` (new `order.manage` policy; `search` on order code or customer name/phone/email, accent-insensitive; `sortBy` `createdAtUtc`|`grandTotal`), `GET /orders/{id}` (customer, request codes, gateway transaction ids) and `POST /orders/{id}/cancel`. Both cancels need a reason (1–500, Q-43) and go through one `OrderCancellation`: order row lock (same as the payment result handler and `OrderExpiryJob`), only `pending_payment` (else `409 order_not_cancellable`), pending payments → `expired` (a late success stays `succeeded` on a cancelled order, manual refund, Q-20), a `held` book-now appointment → `cancelled` (`Appointment.CancelHold`, BR-ORD-12, Q-41). `Order:CancelBlockMinutesAfterPaymentStart` (0, Q-44) can block customers after starting a payment (`409 order_payment_in_progress`). Migration `AddOrderCancellation` (`orders.cancelled_at_utc`, `cancellation_reason`, `ck_orders_cancellation`, `ix_orders_created_at_utc`). Spec: `docs/specs/orders.md` (wave 2).

**Revenue reports (UC-SPA-33) are done in the backend:** `GET /api/v1/reports/revenue` (`groupBy` = `month`|`quarter`|`year`, `productType` = `all`|`service`|`package`, every period of the range returned and clipped, no dates = 1 January to today in Vietnam), `/reports/revenue/by-product` (`top`, default 10, `sharePercent`) and `/reports/revenue/export` (`.xlsx`, 3 sheets), behind the new `report.view` policy (owner; new `Reports` folder). Revenue is the earliest `succeeded` payment of a `paid` order, by the Vietnam date of `paid_at_utc` (Q-46); zero-total orders never count (Q-47); other successful payments (cancelled/expired order, a second success) are returned apart as `unrecognizedPayments` for a manual refund. `IRevenueReportRepository` aggregates per Vietnam day in SQL (`AT TIME ZONE` via `TimeZoneInfo.ConvertTimeBySystemTimeZoneId`); the workbook is built with ClosedXML behind the `IRevenueReportExporter` port. Limits in `appsettings.json`: `Reports:MaxRangeYears` (5), `Reports:MaxTopProducts` (50). Report integration tests seed far-future years (2040+), one per test, because reports add up the shared test database. No migration. Spec: `docs/specs/reports.md`.

**AI assistant (UC-SPA-32) is done in the backend:** `POST /api/v1/ai/chat` (`[AllowAnonymous]`: guests chat without saving, Q-01; customers' turns are saved to `ai_chat_messages`; staff/owner → `403`, Q-60) and `GET /api/v1/me/ai/history` (`before`/`limit` cursor, new `ai.chat` policy, customer). New `AiAssistant` folder: `AiAssistantService` builds the request from the fixed `AiAssistantPrompt`, the customer's last 5 turns and `AiToolCatalog` (8 tools: `search_catalog`, `get_product_detail`, `find_available_slots`, `list_my_appointments`, `list_my_packages`, `suggest_products`, `propose_booking`, `final_answer`); `AiToolExecutor` runs them on the existing catalog/availability/appointment/purchase services (customer always from the JWT, minimal fields, never writes) and collects product cards and booking proposals (`/booking/new?...` links, the assistant never books, Q-64). The model must end with `final_answer { scope, answer }`: `medical` / `out_of_scope` / a provider safety block are replaced by fixed `AiCannedAnswers` and drop the cards (BR-AI-01, 09). The provider sits behind the `IAiChatModel` port: `GeminiAiChatModel` calls the Gemini REST `generateContent` endpoint (no SDK) with function calling mode `ANY`, echoes the model turn verbatim (thought signatures) and loops tools by hand (`GEMINI_API_KEY` → `Ai:ApiKey`; missing key only makes the chat return `503 ai_unavailable`; tests use `FakeAiChatModel`). `AiChatRateLimitFilter` allows 10 questions/60 s and 50/Vietnam day per user or IP (`429 rate_limited`). Limits in `appsettings.json` section `Ai` (`Model` `gemini-3.8-flash`, `TimeoutSeconds` 30, `MaxToolRounds` 4, `MaxQuestionLength` 1000, …). Migration `AddAiChatMessageHistoryIndex`. Spec: `docs/specs/ai-assistant.md`.

Not yet implemented, on purpose: other use-case services, per-customer care history (`/customers/{id}/care-history`, with UC-SPA-26), uploads other than catalog images and in-app notifications (mail is sent synchronously). Folders such as `Seeds` hold only `.gitkeep`. Don't add fake services or sessions to fill them.

## Architecture

**Backend (Clean Architecture)** in `backend/src`, with projects named `NhuNguyetSpa.*`:

- `Domain`: no project or package references. Holds `BaseEntity` (Guid id), `BaseAuditableEntity` (UTC timestamps, Guid actor IDs), `ISoftDelete` and domain exceptions.
- `Application`: references Domain only. It must not reference ASP.NET Core, EF Core or Infrastructure. It holds DTOs, FluentValidation validators, use cases, port interfaces (for example the clock), `OperationResult` and `PagedQuery`/`PagedResult` (default 1/10, PageSize clamped to 1–100). It is wired via `AddApplication()`.
- `Infrastructure`: implements the Application interfaces and is wired via `AddInfrastructure(configuration)`.
- `API`: the composition root ([Program.cs](backend/src/API/Program.cs)). Controllers only translate requests and results. The HTTP response envelope `{ success, message, data, errors, traceId }` is built here, not in Application. The exception middleware maps Validation/BusinessRule→400, NotFound→404, Conflict→409, Unauthorized→401 and anything else→500 without leaking details. Health checks use their own `{ status }` contract. CORS reads `Cors:AllowedOrigins` (no wildcard). Swagger is enabled only in Development or when `Swagger:Enabled=true`. `HttpCurrentUserService` reads real claims.
- Tests: `Domain.Tests`, `Application.Tests` (NSubstitute for the clock) and `IntegrationTests` (WebApplicationFactory, which needs `public partial class Program`). No database is needed.

**Frontend**

- `packages/shared-types`: API response, error, pagination and health contracts. Add a type here only when the backend has a formal contract for it.
- `packages/api-client`: `ApiClient`, `ApiClientError`, `SystemApi`, URL validation, and the query keys plus retry/stale policy shared by both apps (staleTime 60s, at most 1 retry, no polling). An empty response returns `undefined`, so type 204 endpoints as `void`.
- `packages/shared-config`: the strict TS base, ESLint and Prettier configs.
- The packages export TypeScript **source**, which Vite, Metro and the test runners transform directly, so there is no package build step.
- Web UI is **Tailwind CSS v4 + shadcn/ui** (ADR-0005): colors only as tokens in `apps/web/src/styles/theme.css`, screens built from `components/ui` + `components/shared`, and every data table uses the shared `DataTable`. See `apps/web/CLAUDE.md`.
- React components are **not** shared between web (DOM, Tailwind + shadcn) and mobile (React Native). Each platform organises code under `src/features/<feature>`.
- TanStack Query owns server state, Zustand holds client/UI state only, and local React state covers the rest.
- Mobile routing is Expo Router in `apps/mobile/app` with route groups `(public)`, `(customer)` (Tabs), `(staff)` and `(owner)`. Web has Public/Customer/Staff/Owner layouts. Role areas are unprotected public previews: `RouteGuard` is an abstraction kept for the future auth phase, not a security boundary.
- Env: web uses `VITE_API_BASE_URL` (example `https://localhost:7001`) and mobile uses `EXPO_PUBLIC_API_BASE_URL` (example `http://10.0.2.2:5000`, the Android emulator's alias for host loopback). A missing or invalid URL shows a "Configuration Error" and makes no network call, with no fallback. These values are bundled publicly, so never put secrets in them. Web URLs in Docker are fixed at build time.

## Adding a feature

Follow `docs/conventions/workflow.md`. In short:

1. Read or write the spec in `docs/specs/`. Check names in the glossary and add new concepts there first. Unclear rules go in `docs/decisions/open-questions.md` with a configurable default.
2. Backend order: Domain → Application (DTOs, validators, service interface and implementation in `UseCases/<Feature>`, tests) → Infrastructure (EF configuration, migration, repository) → API (thin controller, integration tests).
3. Shared contract: `packages/shared-types` → `packages/api-client` (`<Feature>Api`, query keys).
4. Web and mobile: hooks → components → pages and routes → tests.
